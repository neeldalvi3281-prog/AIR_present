# TOTAL REFORM — Reliable, Low-Resource Whole-Hand Mouse + Palm Rotation Presentation Controller

## IMPORTANT — READ BEFORE EDITING

This is a **major interaction redesign** of the existing project.

Do NOT blindly rewrite the project.

First inspect the existing implementation and understand what is already working, especially the recent **Windows native `SendInput` fix**.

The final system must prioritize these three things, in this exact order:

```text
1. RELIABILITY
2. LOW RESOURCE USAGE
3. LOW LATENCY / RESPONSIVENESS
```

A feature that is theoretically clever but unreliable or computationally expensive is NOT acceptable.

The project is a local/offline Windows presentation controller using:

* Python
* OpenCV
* MediaPipe Hand Landmarker
* deterministic hand geometry
* native Windows `SendInput`
* no cloud AI
* no additional ML model

The current project already has working hand tracking, gesture infrastructure, native keyboard input, and native mouse input.

Your job is to **reform the interaction model**, not rebuild the entire project from scratch.

---

# 1. CORE DESIGN PRINCIPLES

The new implementation MUST follow these principles:

### Reliability first

Prefer:

```text
simple geometry
+
temporal filtering
+
state machines
+
hysteresis
+
dead zones
+
confirmation frames
+
cooldowns
```

over complicated classifiers.

Do NOT use a complicated algorithm merely because it appears more sophisticated.

The system should favor **not triggering an action** over accidentally triggering the wrong action.

A false page change or accidental click is worse than occasionally requiring the user to repeat a gesture.

---

### Low resource usage

The controller is intended to run on an ordinary laptop.

Do NOT add:

* another neural network
* PyTorch
* TensorFlow
* YOLO
* OpenPose
* MediaPipe Holistic
* cloud APIs
* GPU-only processing
* continuous recording
* unnecessary background workers
* large automation frameworks

Reuse the existing MediaPipe Hand Landmarker.

All additional geometry and state calculations should be extremely lightweight.

Target additional processing:

```text
palm geometry        < 0.2 ms/frame
rotation calculation < 0.2 ms/frame
fist classification  < 0.2 ms/frame
mouse mapping        < 0.1 ms/frame
```

The exact numbers are targets, not excuses to sacrifice reliability.

# 5. FINAL USER CONTROLS

## A. Whole-hand mouse movement

The mouse pointer follows the **whole hand/palm**, NOT the index fingertip.

Use a palm/hand anchor calculated from multiple landmarks.

Recommended anchor:

```text
Wrist
Index MCP
Middle MCP
Ring MCP
Pinky MCP
```

Calculate:

```text
palm_center =
(
    wrist +
    index_mcp +
    middle_mcp +
    ring_mcp +
    pinky_mcp
) / 5
```

Do NOT use only:

```text
index fingertip
```

for mouse tracking.

The cursor should feel like the user's whole hand is moving the pointer.

# 7. HAND DISAPPEARANCE

If no hand is detected:

```text
NO MOUSE MOVEMENT
NO CLICK
NO PAGE NAVIGATION
NO ACTION
```

The application simply waits.

When the hand reappears:

```text

```

Do not generate:

* an artificial mouse jump
* an artificial click
* a page navigation event
* a stale rotation event

when the hand re-enters the camera.

Reset or appropriately invalidate temporal state when the hand is absent long enough to prevent stale gestures.

# 9. ACTUAL PALM ORIENTATION MUST BE TRACKED

Do NOT interpret palm rotation using palm movement on the screen.

This is WRONG:

```text
hand moves right → clockwise
hand moves left → anti-clockwise
```

The hand can translate anywhere without rotating.

Instead calculate the **orientation of the palm itself** from the landmarks.

The system must distinguish:

```text
TRANSLATION
```

from:

```text
ROTATION
```

Example:

```text
Move hand right
    ↓
NO page navigation

Rotate palm clockwise
    ↓
NEXT PAGE
```

This distinction is a core reliability requirement.

---

# 10. PALM ORIENTATION CALCULATION

Construct a local palm coordinate system using multiple landmarks.

At minimum use:

```text
Wrist
Index MCP
Middle MCP
Ring MCP
Pinky MCP
```

Do NOT use fragile rules such as:

```text
if landmark_y > fixed_value
```

or any similar fixed image-coordinate shortcut for orientation.

Use normalized geometric relationships.

The orientation calculation must be tolerant of:

* left hand
* right hand
* moderate hand rotation
* moderate translation
* moderate camera perspective
* different hand sizes
* normal landmark jitter

Do NOT add another ML model.

---

# 11. ROTATION ESTIMATION MUST BE STABLE

Use a stable palm reference vector/basis derived from multiple palm landmarks.

Prefer an orientation estimate that is resistant to noise from any one landmark.

For example, construct a palm-direction vector or local palm basis using combinations of:

```text
wrist
middle MCP
index MCP
pinky MCP
```

Use the resulting orientation rather than trusting one finger.

If appropriate, use a robust average/centroid of palm landmarks before determining orientation.

Avoid unnecessary matrix-heavy or computationally expensive operations every frame.

Simple vector math is preferred.

---

# 12. ROTATION ANGLE

Track a continuous palm orientation value.

Conceptually:

```text
previous_angle
       ↓
current_angle
       ↓
signed_angle_delta
```

Handle angle wrapping correctly.

For example:

```text
179° → -179°
```

must be interpreted as approximately:

```text
+2°
```

not:

```text
-358°
```

Use a proper wrapped angular difference calculation.

---

# 13. CLOCKWISE / ANTI-CLOCKWISE MAPPING

Determine the direction from the palm orientation change.

However, **do not blindly assume the mathematical sign convention**.

The camera may be mirrored.

The implementation must explicitly validate:

```text
physical clockwise → NEXT
physical anti-clockwise → PREVIOUS
```

for the actual camera pipeline.

If the camera mirror transforms the sign, compensate in one clearly documented place.

Do NOT scatter sign inversions throughout the code.

---

# 14. ROTATION MUST BE RELATIVE TO A NEUTRAL STARTING ORIENTATION

For reliability, do not require a globally fixed palm angle.

Instead:

```text
stable neutral orientation
        ↓
record baseline
        ↓
measure relative rotation
```

Example:

```text
neutral = +12°
current = +41°

relative rotation = +29°
```

This is a meaningful clockwise rotation.

The neutral orientation may vary naturally between users and camera placement.

This is much more robust than:

```text
if angle > 30° → next
```

---

# 15. ROTATION THRESHOLD

Minor orientation changes must not navigate slides.

Recommended starting point:

```text
min_rotation_degrees = 28°
```

The exact threshold must remain configurable.

The implementation should use hysteresis between activation and release thresholds.

For example:

```text
activation threshold = ~28°
release threshold    = ~10–15°
```

This prevents the state from rapidly bouncing between active and released near the threshold.

Do NOT trigger on tiny angle changes.

---

# 16. ROTATION STATE MACHINE

Use an edge-triggered state machine.

Recommended:

```text
IDLE
  ↓
ROTATION_TRACKING
  ↓
ROTATION_CANDIDATE
  ↓
ROTATION_CONFIRMED
  ↓
TRIGGER
  ↓
COOLDOWN
  ↓
WAIT_FOR_REARM
  ↓
IDLE
```

The exact internal names may differ, but the behavior must remain equivalent.

The purpose is to prevent repeated navigation and false positives.

---

# 17. ROTATION CONFIRMATION

Require multiple consecutive frames before triggering.

Recommended:

```text
rotation_confirm_frames = 4
```

Example:

```text
Frame 1 → clockwise candidate
Frame 2 → clockwise candidate
Frame 3 → clockwise candidate
Frame 4 → confirmed
             ↓
          NEXT PAGE
```

If the direction changes before confirmation:

```text
cancel candidate
```

Do not trigger.

This makes the detector tolerant of noisy landmark estimates.

---

# 18. ROTATION COOLDOWN

After navigation:

```text
NEXT/PREVIOUS
      ↓
COOLDOWN
```

Recommended starting value:

```text
navigation_cooldown_ms = 700
```

During cooldown:

```text
NO SECOND PAGE ACTION
```

unless an entirely separate, valid, re-armed gesture has been established.

# 19. ROTATION RE-ARM

Holding a rotated palm must NEVER repeatedly change pages.

Example:

```text

   ↓
Clockwise 30°
   ↓
NEXT PAGE
   ↓

   ↓
NO ACTION
   ↓
return near neutral
   ↓
RE-ARM
   ↓
clockwise again
   ↓
NEXT PAGE
```

This is mandatory.

The implementation must be edge-triggered rather than level-triggered.

# 27. SEPARATE MOUSE AND ROTATION GEOMETRY

This is extremely important.

### Mouse

Use:

```text
filtered palm centroid
```

because mouse movement benefits from smoothing.

### Rotation

Use:

```text
raw/current landmark geometry
```

or only lightly filtered orientation.

Do NOT calculate rotation from:

```text
filtered mouse X/Y
```

The systems must remain independent:

```text
LANDMARKS
   │
   ├──→ Palm centroid
   │       ↓
   │   One-Euro filter
   │       ↓
   │      Mouse
   │
   └──→ Palm orientation
           ↓
      Rotation detector
           ↓
       Navigation
```

---

# 28. AVOID OVER-FILTERING

Filtering improves stability, but excessive filtering increases latency.

Do NOT:

* stack several moving averages
* use a huge history window
* smooth orientation heavily
* delay every event unnecessarily

Prefer:

```text
minimal smoothing
+
confirmation frames
+
hysteresis
+
state machine
```

This gives reliability without excessive latency.

# 40. THREADING AND MEMORY
