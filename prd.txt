# PRODUCT REQUIREMENTS DOCUMENT

# PRESENTER CONTROLLER

**Version:** 1.0
**Status:** Development Specification
**Platform:** Desktop / Laptop
**Primary Target:** Windows
**Architecture:** Offline-first, local computer vision
**Primary Language:** Python
**Primary Goal:** Reliable, low-latency, low-resource presentation control using natural hand gestures.

---

# 1. PRODUCT OVERVIEW

Presenter Controller is a lightweight desktop application that allows a presenter to control presentations using natural hand gestures captured through a standard webcam.

The system should allow the user to:

* Move between presentation pages using air gestures.
* Control a virtual laser pointer using the index finger.
* Move a pointer/cursor using hand movement.
* Perform click actions using pinch gestures.
* Lock/unlock gesture control.
* Use hand gestures without touching the keyboard or mouse.
* Work with PowerPoint, Google Slides, browser presentations and PDF presentation viewers.
* Operate completely offline.
* Run without continuously displaying the camera feed.
* Consume as few system resources as reasonably possible.
* Automatically adapt to different computers and webcams.

The product should prioritize:

> **Reliability > low latency > low resource usage > feature count**

---

# 2. CORE PRODUCT PRINCIPLE

The system must NOT treat this as a generic AI classification problem.

Use:

```text
Camera
 ↓
Hand Landmark Detection
 ↓
Cheap mathematical feature extraction
 ↓
Temporal filtering
 ↓
Gesture State Machine
 ↓
Action Dispatcher
```

Machine learning is responsible primarily for:

> "Where is the hand?"

Traditional deterministic algorithms are responsible for:

> "What is the user doing?"

This separation is a core architectural principle.

---

# 3. PRODUCT GOALS

## Primary goals

### G1 — Reliable slide navigation

The presenter should be able to change slides naturally without touching the computer.

### G2 — Extremely low accidental activation

Normal hand movements while speaking should almost never trigger slide changes.

### G3 — Low latency

A deliberate gesture should result in the corresponding action quickly enough to feel natural.

### G4 — Low resource consumption

The application should work comfortably on ordinary laptops without requiring a dedicated GPU.

### G5 — Offline operation

No camera data, gesture data or presentation content should need to leave the device.

### G6 — Hardware independence

The system should automatically adjust to different:

* CPUs
* webcams
* resolutions
* lighting conditions
* presenter distances

### G7 — Expandable architecture

New gestures and presentation targets should be addable without rewriting the vision engine.

---

# 9.2 Presentation Mode

The camera preview must disappear.

The application continues tracking in the background.

Visible elements should be limited to:

* optional laser

# 9.3 Disabled Mode

Gesture recognition is completely inactive.

Camera may be released.

No actions can be triggered.

# 9.4 Calibration Mode

Used before the first presentation or when the user requests recalibration.

Calibration should measure:

* hand size
* camera resolution
* movement range
* stationary hand noise
* swipe amplitude
* swipe velocity
* neutral position

Calibration should create a local profile.

# 10. GESTURE SYSTEM

The system should recognize gestures using a **state machine**, not individual frame classification.

---

# 11. SLIDE NAVIGATION

## Next slide

Physical gesture:

```text
OPEN PALM

RIGHT → LEFT
```

This follows the user's preferred page-turn behavior.

## Previous slide

```text
OPEN PALM

LEFT → RIGHT
```

---

# 12. SWIPE VALIDATION

A swipe must satisfy multiple conditions.

Conceptually:

```text
Open palm
+
Hand confidence sufficient
+
Horizontal movement sufficient
+
Horizontal movement dominates vertical movement
+
Direction consistency sufficient
+
Velocity sufficient
+
Gesture duration valid
+
System armed
+
Cooldown expired
=
VALID SWIPE
```

Never trigger based solely on:

```text
x_position changed
```

---

# 13. HAND-SCALE NORMALIZATION

Gesture thresholds must not be fixed solely in pixels.

Calculate:

```text
hand_scale
```

and normalize movement:

```text
normalized_movement =
movement / hand_scale
```

This allows the system to work when the presenter is:

* closer to the camera
* farther from the camera
* using different webcams

---

# 14. SWIPE STATE MACHINE

Required states:

```text
IDLE
 ↓
HAND_DETECTED
 ↓
TRACKING
 ↓
SWIPE_CANDIDATE
 ↓
CONFIRMED
 ↓
ACTION_TRIGGERED
 ↓
COOLDOWN
 ↓
REARM
 ↓
IDLE
```

A single physical gesture must generate at most one slide action.

---

# 15. REARMING

After a successful swipe:

```text
ACTION
 ↓
COOLDOWN
 ↓
WAIT FOR HAND STABILIZATION
 ↓
WAIT FOR NEW TRAJECTORY
 ↓
REARM
```

This prevents:

```text
one swipe
 ↓
NEXT
NEXT
NEXT
```

---

# 16. POINTER MODE

Index finger controls pointer position.

The system tracks:

```text
index fingertip
```

and maps normalized camera coordinates to screen coordinates.

Pointer movement must use smoothing.

---

# 17. LASER MODE

The user can activate a virtual laser pointer.

Architecture:

```text
Index fingertip
 ↓
One-Euro filter
 ↓
screen coordinates
 ↓
transparent overlay
 ↓
laser dot
```

The laser overlay must:

* stay above the presentation
* not steal keyboard focus
* not intercept clicks
* be lightweight
* be disabled immediately when laser mode exits

---

# 18. PINCH CLICK

Gesture:

```text
INDEX + THUMB
     ↓
PINCH
```

Action:

```text
mouse click
```

Use distance normalized by hand scale.

Do NOT use a fixed pixel distance.

---

# 19. LOCK GESTURE

Fist can be used to temporarily lock gesture control.

When locked:

```text
hand tracking continues
gesture actions disabled
```

The application must visually indicate lock status in developer mode.

---

# 20. RESUME / UNLOCK

Thumb-up or designated unlock gesture may resume interaction.

However, the unlock gesture must require:

* confidence
* minimum duration
* stable pose

to prevent accidental unlocking.

---

# 21. GESTURE MODES

Do not recognize all gestures equally at all times.

Use explicit modes.

Example:

```text
PRESENTATION MODE
│
├── swipe
├── lock
└── mode switch

POINTER MODE
│
├── finger movement
├── pinch click
└── exit

LASER MODE
│
└── finger movement
```

Only the gestures relevant to the current mode should be evaluated.

This reduces false positives and CPU work.

---

# 22. GESTURE PRIORITY

If two gestures appear simultaneously:

```text
Mode-specific gesture
>
Emergency/lock gesture
>
Primary presentation gesture
>
Optional gesture
```

The system must never execute multiple conflicting actions from one frame sequence.

---

# 23. CAMERA ARCHITECTURE

Use a configurable camera backend.

Initial implementation:

```text
OpenCV
```

Possible future Windows optimization:

```text
Media Foundation
```

The camera manager must expose:

```text
resolution
FPS
frame timestamp
frame availability
camera status
```

---

# 24. LATEST-FRAME POLICY

Do not maintain an unbounded frame queue.

The application should prefer:

```text
newest frame
```

over:

```text
oldest frame
```

If inference falls behind:

```text
old frames → discard
newest frame → process
```

Goal:

**minimum latency.**

---

The application should eventually automatically adjust:

* camera resolution
* inference frequency
* idle processing rate
* active processing rate

based on:

```text
CPU usage

hand confidence
hand size
frame drop rate
gesture activity
```

Example:

```text
IDLE
↓
low inference rate

HAND DETECTED
↓
medium inference rate

HAND MOVING
↓
high inference rate

POINTER ACTIVE
↓
high continuous rate
```

# 27. RESOLUTION ADAPTATION

The system should eventually test:

```text

480×270
640×360
640×480
```

* detection rate
* confidence
* gesture reliability

Do not automatically assume 1080p is better.

---

# 28. MOTION-AWARE PROCESSING

Future optimization:

Use a very cheap motion signal to determine whether full hand inference needs to run at maximum frequency.

Example:

```text
No motion
 ↓
low inference frequency

Motion detected
 ↓
increase inference frequency
```

Motion detection must NEVER directly trigger a gesture.

It only controls processing frequency.

---

# 29. FILTERING

Use a low-latency adaptive filter such as:

**One-Euro Filter**

Apply filtering primarily to:

* palm center
* index fingertip
* pointer position

Do not over-smooth swipe detection because excessive smoothing creates latency.

---

# 30. RELIABILITY ENGINE

The reliability engine must monitor:

```text
hand confidence
trajectory consistency
movement amplitude
movement velocity
hand scale
gesture duration
cooldown
rearm state
```

Every gesture should have a confidence/validity decision.

---

# 31. FALSE-POSITIVE PREVENTION

Normal speaking gestures must not change slides.

Use:

```text

direction consistency
horizontal/vertical ratio
velocity
hand pose
confidence
cooldown
rearm
mode
```

Do not rely on a single threshold.

# 46. SOFTWARE DESIGN PRINCIPLES

The project must follow:

### Separation of concerns

Vision must not directly control PowerPoint.

Correct:

```text
Vision
 ↓
Gesture
 ↓
Action
 ↓
Controller
```

Incorrect:

```text
MediaPipe callback
 ↓
press right arrow
```

---

### Replaceable components

The system should allow:

```text
MediaPipe
```

to eventually be replaced by another hand-tracking backend without rewriting the gesture engine.

Gesture logic should be testable without a webcam.

The GestureEngine should accept landmark data.

Therefore:

```text

 ↓
GestureEngine
 ↓
gesture result
```

can be tested offline.

The system should identify one stable hand and follow it.

This is deliberate because one-hand tracking provides:

* lower complexity

* fewer false gestures

# 56. DEFINITION OF DONE — V1

The product is considered complete when the user can:

1. Launch the application manually.
2. Allow it to detect the webcam.
3. Complete calibration.
4. Open PowerPoint.
5. Start a presentation.
6. Put the laptop at a normal presentation distance.
7. Swipe right → left.
8. Move to the next slide.
9. Swipe left → right.
10. Move to the previous slide.
11. Speak naturally and move their hands without accidental slide changes.
12. Activate pointer mode.
13. Move the pointer using their index finger.
14. Use pinch to click.
15. Activate a laser pointer.
16. Present without seeing the camera preview.
17. Use the system without internet.
18. Disable gesture control instantly with the emergency key.
19. Exit without crashes.

# 57. SUCCESS METRICS

The most important metrics are:

### Reliability

How often does an intentional gesture produce the correct action?

### False activation rate

How often does normal movement trigger an action?

### Latency

Time between physical gesture completion and action.

### CPU

Average CPU consumption.

### Memory

RAM consumption.

### Portability

How well does it operate across different machines and webcams?

# 58. PRODUCT PRIORITY

When two requirements conflict:

```text
1. Reliability
2. Safety / accidental activation prevention
3. Latency
4. Low CPU usage
5. Portability
6. Feature richness
7. Visual polish
```

Never sacrifice reliability merely to add another gesture.

# 59. FINAL PRODUCT PHILOSOPHY

Presenter Controller should feel like:

> **A invisible computer peripheral controlled by your hand.**

It should NOT feel like:

> "A computer-vision demo running a webcam."

The user should launch it, calibrate once, start presenting, and forget that the software exists.

The ideal experience is:

```text
Launch
  ↓
READY
  ↓
Present
  ↓
🖐️ ← → 🖐️
  ↓
Slides change naturally
  ↓
No visible camera
  ↓
No internet
  ↓
No noticeable lag
  ↓
No accidental actions
```

The technology should disappear behind the experience.
